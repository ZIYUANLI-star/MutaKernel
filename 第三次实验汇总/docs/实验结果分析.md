## 三、基线未通过的原因分类

### 3.1 CUDA-L1（101/231 基线失败，44%）

| 类型 | 数量 | 原因 |
|------|------|------|
| **A1. CUDA OOM** | 19 | 极端 stress 输入（4-8 GB tensor）× 94 个 worker 子进程，H20 141GB 也不够同时分配 |
| **A2. 入口类缺失** | 13 | `module has no attribute 'Model'`——kernel source 的入口类名不是 `Model`/`ModelNew`，框架无法加载 |
| **A3. 其他运行时错误** | 3 | 其他 Worker crash（总计 Cat A = 35）|
| **B. 边界精度差异** | 4 | 正常输入下 max_diff 略超 atol=0.01，压力下也只多几个 case |
| **C. 真正数值错误** | 62 | baseline 失败 + 增强测试发现大量差异（disc>20），kernel 数值实现有根本性错误 |

### 3.2 AI CUDA Engineer（25/222 基线失败，11%，补跑）

| 类型 | 数量 | 原因 |
|------|------|------|
| **全部 fail（baseline 0 pass）** | 21 | CUDA kernel 与 PyTorch 参考实现语义不一致（LLM 生成的 kernel 数值逻辑错误）|
| **部分 fail（baseline mixed）** | 4 | 部分输入尺寸下精度退化 |

> **注**：补跑版本已筛选掉原始数据集中 `Correct=False` 的 kernel，仅测试标记为正确的子集。因此 baseline 通过率从第一次的 14% 提升至 **89%**。

### 3.3 TritonBench-G（39/138 基线失败，28%，补跑+修复）

| ref_mode | 完成 | Baseline 全通过 | Baseline 失败 | 失败率 |
|----------|------|----------------|-------------|--------|
| pytorch_ref | 26 | 10 | 16 | 62% |
| self_ref | 112 | 89 | 23 | 21% |

- **pytorch_ref 失败率高（62%）**：Triton kernel 与 PyTorch 参考实现之间存在语义差异（不同算法/精度），属于真正的差分检测结果
- **self_ref 失败率低（8%）**：同一 kernel 对自身做差分，仅在非确定性或 config 变化时产生差异

### 3.4 NVIDIA/apex（1/1 基线失败）

apex 只有 1 个新 kernel（`apex__mlp`），baseline 全部 fail，且增强测试发现 92 个差异，属于真正数值错误。

## 五、TritonBench-G 按 ref_mode 详细分析

| 指标 | pytorch_ref（26 个） | self_ref（112 个） |
|------|--------------------|--------------------|
| Baseline 全通过 | 10 (38%) | 89 (79%) |
| 增强测试发现差异 | 2/10 (20%) | 9/89 (10%) |
| 跳过（baseline_all_error） | 0 | 3 |

## 七、结论

1. **增强测试能有效发现基线遗漏的隐性 bug**：CUDA-L1 46%、AI CUDA Engineer 25%、TritonBench-G 11% 的基线通过 kernel 在增强测试下暴露了数值问题。三个数据集的检出率差异反映了 kernel 来源的质量梯度：RL 优化 > LLM 生成 > 真实开源代码。

2. **极端量级输入 + 训练模式是最有效组合**：`[value_stress, training_stress]` 联合触发覆盖了 CUDA-L1 65%、AI CUDA Engineer 64%、TritonBench-G 36% 的增强失败 kernel。极端量级 policy（`extreme_magnitude`、`near_overflow`、`reduction_adversarial`）在所有数据集中均位居触发次数前三。

3. **非确定性问题比预期更普遍**：补跑后共发现 **14 个** 非确定性 kernel（CUDA-L1 2 个，AI CUDA Engineer 7 个，TritonBench-G 5 个），远多于第一次实验的 3 个。其中 TritonBench-G 的 5 个全部是 attention 相关 kernel（flash_attn、causal_attn 等），这与 GPU 上 attention 计算的 warp-level 浮点归约顺序不确定性一致。

4. **数据适配效果显著**：
   - AI CUDA Engineer baseline 通过率从 14% → 89%（签名修复 + 质量筛选）
   - TritonBench-G 有效测试规模从 18 → 138 个（7.7× 提升），经二次修复后仅剩 3 个不可修复的 skip

5. **RL 优化 kernel 的隐性精度问题最严重**：CUDA-L1 的增强检出率 46% 远高于其他数据集，说明 RL 优化在追求性能时系统性地牺牲了数值边界正确性。这些 kernel 在正常输入下表现正确，但在极端输入下（±1e6、近溢出值）暴露大量精度退化。

6. **TritonBench-G self_ref 模式验证了非确定性检测能力**：即使无法进行 kernel-vs-PyTorch 的差分比较，self_ref 模式通过 repeated_run 维度仍可检出 5 个非确定性 kernel，证明了该模式在缺少参考实现时的实用价值。

## 八、遗留问题与建议

1. **TritonBench-G 仅剩 3 个不可修复 skip**：problem_9 (rope_embedding)、problem_36 (attention_score)、problem_69 (mixed_sparse_attention) 在 GPU 上 Triton kernel 编译/运行时崩溃，属于 kernel 本身与 H20 GPU 的兼容性问题
2. **TritonBench-G registry.json 路径分隔符**：师兄 Windows 生成的 JSON 使用反斜杠，本次已手动修复，建议在生成脚本中统一使用正斜杠
3. ~~AI CUDA Engineer 旧 detail 文件残留~~：已清理，当前 222 个 detail 文件与 checkpoint 完全匹配
4. **修复的 15 个 self_ref kernel 全部 baseline fail**：这些 kernel 的 Model（原始）和 ModelNew（CUDA/Triton）在参数传递方式上有差异导致数值结果不同，但至少能正常执行不再崩溃。其中 `problem_154` (fused_rotary_embedding) 在增强测试中发现了 86 个差异
