> 创建日期: 2026-07-21

## 1. 要证明的核心命题

> 改进来自"由故障诊断导出的定向性"，而不是"多跑了测试"。

因此一切主对比必须预算匹配（equal candidate-invocation + equal GPU-time 双口径），
并配 leave-one-dimension-out 分析（首杀计数会低估被多维同时覆盖的维度贡献）。

## 3. 本轮评估提出的三点矩阵修正建议

1. **补一行 unrestricted MutaKernel full-suite（原生协议、不限预算）**。
   32 调用的预算匹配行显著弱于历史协议（value_stress 单维历史就 45–75 轮、
   repeated 10 次 → 2 次、config 7 batch → 4 batch）。fairness gates 本就要求
   三视图（native 不限 / equal-call / equal-time），执行时不要省掉第一视图，
   否则与 RQ1 审计和历史 pilot 数据失去连接，且 32 调用行可能测不出
   repeated_run 类缺陷（TritonBench-G 的竞态在历史数据里需要多次重跑暴露）。
2. **mutakernel-full 的 32 个 case 是每策略 1 seed，方差敏感**。至少为
   预算匹配行补一个种子敏感性附录（换 3 组种子重跑一个子集）。
3. **backward VJP（train 模式 requires_backward）是范围扩张**。历史方法不查反向。
   保留它有价值（LLM kernel 常忘写 backward），但要：契约按任务门控、结果单列、
   论文明确它是 V2 的扩展贡献而非历史方法复现。

## 4. 队列与计划（两个必须分开冻结的对象）

1. **population/applicability 计划**（RQ1 用）：覆盖完整自然 kernel 帧
   （名义 597，需先做 831/64 vs 834/67 的 stable-ID 对账），保留 unsupported /
   missing / partial / inconclusive 分层。**该 planner 尚未实现，是最大代码缺口。**
2. **paired rich-contract 计划**（RQ2 用）：只含能执行全部矩阵 case 的公共子集。
   现有 strict planner 已实现，但要预先评估子集规模——dtype 兼容性历史数据显示
   AI-CUDA-Engineer 仅 42/222、CUDA-Agent 仅 109/176 支持非 fp32，配对子集可能
   显著缩小，论文必须报告子集构成，并考虑"能力分组配对"（相同能力组内配对比较）
   而非单一全能力子集，避免 RQ2 结论只覆盖少数任务。

## 5. 统计方案（采纳并已实现）

- 抽样单元 = task/kernel（任务聚类），不把同任务的变异体/测试当独立样本；
- task-cluster bootstrap 置信区间（10,000 次重抽）；
- 同一 subject 被两个验证器评估 → paired exact McNemar；多重比较 Holm 校正；
- 告警精度只用审计确认的告警计算；INCONCLUSIVE 做敏感性边界（全当缺陷/全当
  非缺陷两个极端）；
- 主指标与排除规则在跑全量前冻结（预注册纪律）。

## 6. 开销报告（FSE 口径）

- 每策略行报告：candidate 调用数、GPU 秒、冷编译时间与热执行时间分离、
  首反例时间、每确认缺陷的 GPU 秒；
- detection/cost Pareto 图替代 V1 的"系统吞吐"叙事；
- 现有 process-per-case runner 只能给冷路径成本；稳态 ADRS 开销需要
  compile-once/session runner，或在论文中明确冷/稳态分开报告并把稳态留作
  局限。**不建议为 FSE 版本专门开发 session runner**（性价比低），
  冷路径 + 明确声明即可。

## 7. 泛化样本（回应 Reviewer B Q4）

有界扩展：至少 1 个 L3 或多 kernel/带状态/反向子集，CUDA + Triton 双语言，
按任务级报告；做不完就在 scope limitation 明确声明，不沉默。
