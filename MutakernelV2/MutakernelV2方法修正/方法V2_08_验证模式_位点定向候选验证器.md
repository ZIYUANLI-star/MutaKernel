## 一、问题背景

V1 把验证器定义成"接收 EMD 未关闭的变异体"（Section 5 原文），
导致审稿人认定验证新 kernel 需要先做变异——这是 Reviewer A 的核心批评。
GPT5.6sol 的 FSE 重构已把在线验证剥离为纯 candidate+reference 接口
（`_candidate_worker.py`），但矫枉后损失了一块价值：**变异研究对在线验证
不再有任何逐候选的指导作用**，固定策略矩阵对所有候选一视同仁，
"为什么需要变异"的回答力度随之变弱。

作者的定位纠正（2026-07-21 网页讨论）给出了正确的综合：待验证对象是
原始候选内核；变异知识以**静态位点匹配 + 离线映射查表**的形式进入在线
路径（零探针执行成本），即思路文档 00 §2.1 的方案 (c)。

## 二、本模块拟解决的问题

给定 (candidate K, reference R, contract, budget)，输出可复放、可解释的
验证判定：

1. **定向性**：优先测试 K 的代码位点上实际存在的故障类的已验证定向策略
   （查 FaultToStressMap），而非盲跑全套件；
2. **验收语义**：FAIL 附反例复放包与修复反馈；PASS 附"已覆盖故障类清单"
   （mutation adequacy 语义），永不声明 correct；
3. **可部署性**：首败早停、冷/热成本分离、命令行 + Python API 双接口、
   结构化 error feedback 可直接喂给 ADRS 循环的 LLM 修复。

## 三、方法设计

### 3.1 接口

```
validate(candidate_path, reference_path, contract, budget_profile,
         map: FaultToStressMap, mode: "deploy"|"evaluate") -> ValidatorReport

budget_profile ∈ {fast: 8 calls, standard: 32 calls, full: 不限（全 map 相关 case）}
mode=deploy   : 首个 SPEC_VIOLATION 即停（返回反例）
mode=evaluate : 跑完计划（供 RQ2/RQ4 评测与交叉确认分析）
CLI: exit 0 = PASS, 1 = FAIL, 2 = INCONCLUSIVE；报告 JSON 落盘
```

### 3.2 位点定向选择（核心新增层）

```
function SelectPlan(K, contract, budget, map) -> plan:
    fp ← BuildSiteFingerprint(K)                     # M3 静态，<50ms
    present ← fp.fault_classes_present                # 剔除先验等价位点后
    # ── 第一段: 定向 case（按性价比排序）──
    directed ← []
    for F in present（按 map 中 max closure_rate 降序）:
        for c in map.entries[F].effective_cases（closure_rate 降序）:
            if contract 授权 c 且 c ∉ directed:
                directed.append(c 附 seeds 派生规则)
    # ── 第二段: 通用兜底（防指纹假阴性: 无已知位点 ≠ 无错误）──
    general ← 通用 case 序列（跨故障类 sole_detector 加权的固定顺序,
               随 map 版本冻结; 含 iid、repeated、dtype、config 各至少 1）
    plan ← take(directed, ceil(0.7×budget)) ++ take(general\directed, 其余预算)
    附: 每 case 的 seed = hash(subject_id, case_id) 派生（确定性、可复现）
    return plan
```

设计裁定：

- **只排序，不排除**：指纹 `count=0` 的故障类不被禁测，只是排到通用段——
  LLM 可以写出算子模式之外的错误，指纹的假阴性由 30% 通用预算兜底；
- **确定性与预注册兼容**：plan 是 (K, contract, budget, map_version,
  fingerprint_version) 的纯函数——不同 subject 的计划不同，但派生规则
  预先冻结，满足配对比较的可复现要求（RQ2 中 site-directed 作为一行
  预算匹配策略参赛）；
- **成本感知**：同 closure_rate 下按 mean_cost_ms 升序（快的先跑），
  优化 time-to-first-counterexample。

### 3.3 执行与判定

```
result ← CSE.run_validate(K, R, contract, plan, early_stop=(mode=="deploy"))
# 两路差分（V2-06 §3.2 退化形式），全部走 M1 严格基座
```

### 3.4 验收语义与报告（ValidatorReport, V2-00 §3.9）

**FAIL**：附首个（deploy）或全部（evaluate）CounterexampleBundle；
`feedback_for_repair` 给出策略语义描述、输入摘要、diff 统计——供 ADRS
循环的 LLM 修复使用（结构化，不给自然语言结论）。

**PASS** 的强制措辞模板：

> "在契约域内、{budget} 预算下未发现反例。已针对该内核存在位点的故障类
> {F-EPS(2 位点), F-SYNC(1 位点)} 执行定向策略
> {near_zero×3, repeated_run×3, …}，其在受控故障上的历史闭合率为
> {0.61, 0.85}。未覆盖的已知故障类: {…}。"

——把 mutation adequacy 语义带进验收结论：这不是"K 正确"，而是
"针对 K 最可能犯的错的定向考卷，K 通过了"。这同时是对
Reviewer A "直接审计无法回答何时该停"的产品化回答。

**INCONCLUSIVE**：按 M1 类别分列（编译失败/契约不支持/超时…），
ADRS 集成方可据此决定重试或人工介入。

### 3.5 与 ADRS 循环的集成（RQ5 支撑）

```
生成循环: LLM 产候选 → validate(fast) → FAIL 反馈 → LLM 修复 → …
                                → PASS(fast) → validate(standard) 终验
守卫: 修复结果须过结构守卫（禁 PyTorch fallback / dead kernel——
      继承 TaskD 严格审查的作弊清单，做成静态检查器）
计费: 每次调用报告 cold_compile_ms 与 warm_ms 分离；
      循环级报告 GPU 秒/候选、time-to-first-counterexample
```

### 3.6 评测协议位（RQ2/RQ4 中的角色）

| 策略矩阵行 | 说明 |
|-----------|------|
| mutakernel-site-directed | 本模块 standard 档（32 calls，plan 由 §3.2 派生） |
| mutakernel-full | 无指纹先验的全套件（= 方案 a，消融对照） |
| 两行差值 | "变异知识的逐候选净贡献"——RQ2 的新增核心声明 |

## 四、架构与流程

```
candidate K + reference R + contract + budget
        │
  [M3] BuildSiteFingerprint(K)          ← 静态、零执行
        │
  [§3.2] SelectPlan（查 FaultToStressMap，70% 定向 + 30% 通用）
        │
  [M6] CSE 两路差分（deploy: 首败停 / evaluate: 跑全）
        │
  ┌─────┼──────────────┐
 FAIL   PASS         INCONCLUSIVE
 +反例  +覆盖清单     +类别
 +修复反馈
```

## 五、桥接接口

| 方向 | 接口 |
|------|------|
| M8 → M3 | `BuildSiteFingerprint(source)` |
| M8 → M7 | 消费 `FaultToStressMap`（版本校验：map_version ↔ fingerprint_version 的算子版本一致） |
| M8 → M6 | `run_validate(…)` |
| M8 → M9 | evaluate 模式告警 → 审计队列 |
| M8 → ADRS | CLI exit code + ValidatorReport + feedback_for_repair |

## 六、与 V1 的差异摘要

| 维度 | V1 Section 5 | V2 M8 |
|------|-------------|-------|
| 输入 | EMD 未关闭的变异体 | candidate + reference + 契约 + 预算 |
| 变异的角色 | 流程内组件（概念混淆） | 静态指纹 + 离线映射查表（零探针执行） |
| 策略选择 | Tier + 算子白名单（针对变异体） | 位点定向 70% + 通用兜底 30%，纯函数派生 |
| 输出 | killed/confirmed_equivalent/survived | FAIL(反例)/PASS(覆盖清单)/INCONCLUSIVE(类别) |
| 早停 | 跨维不早停（审计需求混入） | deploy 首败停 / evaluate 跑全 |

## 七、实现注意

1. map 与指纹的版本一致性在启动时强校验（算子版本 hash 不一致即拒绝运行），
   防止"旧映射 + 新算子"静默错配；
2. 70/30 预算切分与 12-case 通用兜底序列已定案冻结为 v1 默认值
   （2026-07-21，`src/validator/site_directed.py`）；作为超参进 run
   manifest，RQ2 附 50/50、90/10 敏感性行（低成本，只改 plan 派生）；
   **planner 集成时序定案**：site-directed 行的 planner 集成与 audit
   harness 一起排在 P2 阶段——它依赖 FaultToStressMap artifact，而 map
   依赖 Phase I/II 重跑，提前集成没有输入数据；派生纯函数
   （`derive_site_directed_plan`）已实现并测试锁定，预注册时把
   （派生规则版本 + map 版本 + 指纹版本）一并冻结即可满足配对比较要求；
3. deploy 档的报告也要保留全部已执行 case 的 Observation（哪怕早停），
   否则覆盖清单不可审计；
4. 非 KernelBench 结构的候选（无 Model 包装、多文件）需要 M3 提到的
   源码定位适配器，V2 范围内先支持 KernelBench/RQ4 四数据集的既有格式；
5. `feedback_for_repair` 不包含 reference 输出本体（防 LLM 直接拟合
   目标输出的作弊路径），只给差异统计与输入特征描述。
