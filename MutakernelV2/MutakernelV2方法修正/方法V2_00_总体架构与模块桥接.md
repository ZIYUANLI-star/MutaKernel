## 一、问题背景

### 1.1 V1 的结构性缺陷

V1（EuroSys #303 被拒版本）把三种不同性质的活动写进了同一条流水线：

1. **测量**：用变异体测量 KernelBench 式验证器的盲区（研究活动）；
2. **等价判定**：用 EMD 给变异体打二值等价标签（被当作接近 ground truth 使用）；
3. **验证**：把五维压力测试部署为更强的候选内核验证器（系统产品）。

Figure 1(b) 把 Mutation Generation 画进在线 Enhanced Validator，Section 5 又写
"MutaKernel takes as input every mutant that EMD did not close"——三位审稿人
由此认定：验证一个新 kernel 需要先生成变异体（概念混淆）、结论依赖启发式
EMD（严格性缺失）、且没有同预算强基线与开销（实证缺失）。

此外，拒稿后的代码审计发现 V1 执行基座存在真实的 soundness 缺陷
（Phase I 参考/变异模型初始化 RNG 不同步、Phase II 权重按形状顺序拷贝、
输入对象共享、oracle 强转 dtype 等），历史核心数字（939/534/166/222）
全部降级为 pilot 证据（详见 `docs/LEGACY_RESULT_VALIDITY.md`）。

### 1.2 V2 的统一命题

> KernelBench 式验证器把五维正确性行为空间（数值分布 × dtype × 执行模式 ×
> 重复执行 × batch 配置）压缩在单个默认采样点上，因此真实存在的故障可能
> 未被激活、感染、传播或观察到。V2 系统地**测量**这些盲区，把盲区的逃逸
> 机制转化为**定向压力策略**，并检验定向策略在同预算下是否优于朴素增强、
> 在真实内核上能否发现被独立确认的缺陷。

两条铁律贯穿全部模块：

- **R1（对象铁律）**: 最终待验证对象自始至终是"已被现有验证器判定通过的
  原始候选内核"。变异体只是故障探针（fault probe），任何模块不得把变异体
  当作验收目标。
- **R2（证据铁律）**: 一切硬结论（validator gap 数、false-acceptance 下界、
  mutation score 分母、平反判定）必须由**机器可复放的具体反例**支撑；
  EMD 置信度、LLM 判断只能用于预算分配与排序等软用途。

## 二、总体架构

### 2.1 模块清单

| 模块 ID | 名称 | 文档 | 一句话职责 |
|---------|------|------|-----------|
| M1 | 执行基座（Validation Core） | 方法V2_01 | 状态/RNG 严格控制的成对执行 + 严格 Oracle + 三值结果 |
| M2 | 任务契约与输入策略库 | 方法V2_02 | 可执行正确性契约（schema v1）+ 21 种确定性数值策略 + 4 类执行上下文变换 |
| M3 | 变异探针生成与位点指纹 | 方法V2_03 | 16 算子生成一阶故障探针（离线）；`find_sites()` 静态位点指纹（在线） |
| M4 | RealismGuard 与分类学维护 | 方法V2_04 | 探针的构造效度验证（双人编码）+ 故障分类学演化闭环 |
| M5 | EMD 等价证据链 | 方法V2_05 | 四层证据采集 → 证据向量 / 有序等级 / 校准研究 三层输出 |
| M6 | 反例搜索引擎（CSE） | 方法V2_06 | 对象无关的五维反例搜索 + 三路/两路差分判定 |
| M7 | 审计模式 Harness（Mode A） | 方法V2_07 | 盲区测量、平反、逃逸机制归类、FaultToStress 映射产出 |
| M8 | 验证模式 Validator（Mode B） | 方法V2_08 | 位点定向的候选内核验证器（部署组件） |
| M9 | 人工审计与统计桥接 | 方法V2_09 | 双盲标注队列、标签汇编、预算匹配统计的接口规范 |

### 2.2 两种运行模式

```
┌────────────────────────  Mode A: 离线审计（研究活动，一次性） ────────────────────────┐
│                                                                                      │
│  KernelBench 任务 + LLM 生成语料                                                      │
│        │                                                                             │
│   [M2] 契约冻结 ──► [M3] 探针生成(1,646) ──► [M1] 基线执行 ──► killed / survived     │
│        │                                          │                                  │
│   [M4] RealismGuard（探针 ↔ 真实 LLM 错误的构造效度）                                  │
│                                                   ▼                                  │
│                              [M5] EMD 证据链（survived → 等级 + q_pre）              │
│                                                   ▼                                  │
│               [M7] 审计 Harness：按 EMD 等级分配预算 ──► [M6] CSE（三路差分）         │
│                                                   ▼                                  │
│        反例（spec violation）┬── 确认 validator 盲区（RIPR 逃逸机制归类）             │
│                              └── 探针曾判 LIKELY_EQUIVALENT → 平反（false equivalent）│
│                                                   ▼                                  │
│                    [M9] 双盲人工审计（独立确认） + 统计分析                            │
│                                                   ▼                                  │
│   ★ 产物: FaultToStressMap v2（故障类 → 逃逸机制 → 已验证定向策略）★                  │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                        │
                     唯一箭头: FaultToStressMap（版本化 JSON artifact）
                                        ▼
┌────────────────────────  Mode B: 在线验证（部署组件，每候选调用） ─────────────────────┐
│                                                                                      │
│  candidate K + reference R + 契约 + 预算                                              │
│        │                                                                             │
│   [M3-静态] 位点指纹（find_sites，毫秒级，不编译不执行任何探针）                       │
│        ▼                                                                             │
│   [M8] 查 FaultToStressMap → 定向选择/排序策略 case                                   │
│        ▼                                                                             │
│   [M6] CSE（两路差分: K vs R）→ [M1] 执行                                             │
│        ▼                                                                             │
│  FAIL(反例+复放包) / PASS(+已覆盖故障类清单) / INCONCLUSIVE(分类原因)                  │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

Mode B **不含**任何 mutation 生成、探针执行、EMD、Tier、等价标签。
Mode A 与 Mode B 共享 M1/M2/M6 三个基础组件；差别只在被测对象、oracle 结构
（有无 original 对照）、预算分配先验（EMD 等级 vs 位点指纹）与早停策略
（审计不跨维早停 / 部署首败即停）。

### 2.3 "先验引导预算"的对偶

| | Mode A 审计 | Mode B 验证 |
|---|---|---|
| 先验来源 | EMD 证据等级（动态，来自探针自身的历史测试） | 位点指纹（静态，来自候选内核源码） |
| 预算含义 | 该探针值得投入多少反例搜索轮次 | 该候选优先测哪些故障类的定向策略 |
| 失误代价 | 浪费轮次 / 漏掉一个平反机会 | 浪费轮次 / 定向策略排序次优 |

两者是同一思想的两个实例，论文用统一术语 **prior-guided budgeting** 表述。

```json
{
```

### 3.4 ThreeWayObservation（M6 审计模式判定单元，扩展 Observation）

```json
{
  "case_id": "…", "probe_id": "…",
  "A_original_ok": "PASS|FAIL|INCONCLUSIVE",
  "B_mutant_ok":   "PASS|FAIL|INCONCLUSIVE",
  "C_exact_equal": true,
  "verdict": "SPEC_VIOLATION | EXACT_DIVERGENCE_ONLY | INDISTINGUISHED |
              INVALID_INPUT | ACCIDENTAL_REPAIR | INCONCLUSIVE",
  "counterexample_id": "verdict==SPEC_VIOLATION 时必有"
}
```

五值判定语义（详见 方法V2_06 §3）：

| A | B | C | verdict |
|---|---|---|---------|
| PASS | FAIL | * | SPEC_VIOLATION（唯一计入盲区/平反/杀死的结果） |
| PASS | PASS | false | EXACT_DIVERGENCE_ONLY（只推翻严格等价） |
| PASS | PASS | true | INDISTINGUISHED（提升经验等价证据） |
| FAIL | FAIL | * | INVALID_INPUT（该轮作废，单独计数） |
| FAIL | PASS | * | ACCIDENTAL_REPAIR（罕见；转入 original 缺陷线索） |

## 五、全局纪律（各模块文档均须遵守）

1. 三值结果（PASS/FAIL/INCONCLUSIVE），基础设施失败永不计入缺陷或等价证据；
2. 所有随机性来自显式 seed；所有 case 由确定性规则派生并预注册冻结；
3. 每次运行写 run manifest（commit、环境指纹、契约/策略/算子/Map 版本、
   种子、预算、排除项）；历史目录不可变，新旧 checkpoint 不混合；
4. 措辞纪律：`unfalsified` 不写 `confirmed_equivalent`；
   `stress-flagged` 不写 `defective`（直至独立审计确认）；
   `machine-proven` 保留给源码恒等/静态规则。
